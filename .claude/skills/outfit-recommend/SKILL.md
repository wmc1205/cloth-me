# 주간 코디 추천

## 입력
- 옷장 목록: `[{ id, category, name, colors, seasons, styles }]` (사진 자체가 아니라 **태그 데이터**를 보낸다)
- 사용자 프롬프트: 예) "이번 주 출근룩, 비 오는 날은 방수되는 걸로"
- 날씨: 요일별 최저/최고 기온, 강수 여부 (날씨 연동 전에는 생략 가능)

## 출력 JSON 형식 (Zod로 검증)
```json
{
  "week": [
    {
      "day": "mon",
      "items": { "outer": "item_12", "top": "item_3", "bottom": "item_7", "shoes": "item_20", "etc": [] },
      "reason": "쌀쌀한 아침을 고려해 가벼운 아우터를 추가했어요.",
      "shoppingHints": [
        { "category": "bottom", "query": "베이지 와이드 슬랙스", "why": "상의와 톤이 맞는 하의가 부족해요." }
      ]
    }
  ]
}
```
- `day`: `mon | tue | wed | thu | fri | sat | sun` (7개 모두 필수)
- `items`의 값은 **입력으로 준 옷장의 id만** 사용한다. 없는 id를 만들면 안 된다.
- `shoppingHints`는 선택 사항이며, 최대 2개. 상품이 아니라 **검색어**만 담는다. (→ `shopping-recommend`)

## 규칙
1. 같은 옷은 일주일에 **2번 이하**로 쓴다. 옷이 부족하면 `reason`에 이유를 쓴다.
2. 상의/하의는 필수. 신발은 있으면 포함. 아우터는 날씨가 필요할 때만.
3. 계절(`seasons`)이 날씨와 맞지 않는 옷은 제외한다.
4. 사용자 프롬프트의 조건(TPO, 스타일)을 **가장 우선**한다.
5. 옷이 너무 적어서(상의/하의 각 2벌 미만) 7일을 못 채우면, 억지로 만들지 말고 가능한 일수만 반환하고 이유를 알린다.
6. 응답은 JSON만 반환한다.

## 서버에서 하는 후처리 (AI를 믿지 않는 부분)
- 반환된 모든 item id가 사용자의 옷장에 실제로 존재하는지 확인한다. 없으면 해당 항목 제거 후 재시도.
- 같은 옷이 3회 이상 쓰였는지 검사한다.

## 평가 세트 (품질 관리)
- 프롬프트 변경 시 아래 시나리오로 결과를 비교한다. (`tests/fixtures/outfit/`)
  - 출근룩 / 데이트룩 / 운동 / 비 오는 날 / 포멀(결혼식)
- 에이블리 계열 앱에서 "TPO별 추천에서 캐주얼만 나온다"는 불만이 있었다. 포멀/세미캐주얼 시나리오가 실제로 다르게 나오는지 꼭 확인한다.
