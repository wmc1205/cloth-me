# Git 컨벤션

## 브랜치 이름
| 상황 | 형식 | 예 |
|---|---|---|
| 큰 분류의 **새 기능** | `feature/<간략한-설명>` | `feature/weekly-outfit` |
| 이미 있는 기능의 **추가·개선** | `fix/<기능이름>_<추가·개선 내용>` | `fix/outfit_weather-aware-recommend` |

- 영문 소문자·숫자·하이픈. 기능 이름과 설명 사이만 `_`로 구분한다.
- 티켓 1개 = 브랜치 1개 = PR 1개. 한 브랜치에 다른 기능을 섞지 않는다.
- `main`에는 직접 커밋·푸시하지 않는다.

## 흐름
1. **시작**: 새 기능이면 최신 `main`에서 위 규칙대로 브랜치를 만든다. (`git switch main && git pull && git switch -c <이름>`)
   - 작업 중인 변경이 있으면 먼저 아래 2번으로 커밋한다.
2. **기능을 바꿀 때 자동 커밋**: 다른 기능으로 넘어가기 직전, 현재 브랜치의 변경을 `feat|fix|docs|refactor|test: ...`로 커밋한다. 그 다음 새 브랜치를 만든다.
   - 커밋은 의미 단위로 나눈다(쇼핑 전환 / 태깅 / 추천처럼). 한 덩어리로 뭉치지 않는다.
   - `.env*`, 키·토큰이 든 파일(`.mcp.json` 등)은 스테이징하지 않는다. `git add -A` 대신 파일을 지정한다.
   - 커밋 전 `git status`로 무엇이 들어가는지 확인한다.
3. **완료**: `pr-checklist`의 자동 점검(tsc, lint, test, build)이 통과하면 브랜치를 푸시하고 PR을 만든다. 점검이 실패하면 PR을 만들지 않고 먼저 고친다.
4. **리뷰**: PR을 만든 뒤 `reviewer` 에이전트(읽기 전용)로 코드 리뷰를 돌리고, 결과를 PR 코멘트로 남긴다.
   - 개선할 사항을 "반드시 수정 / 권장 / 참고"로 나눈다.
   - 코드를 고친 작성자와 검토자는 분리한다. `reviewer`가 직접 고치지 않는다.
   - "반드시 수정"은 같은 브랜치에 커밋으로 반영하고 다시 리뷰한다.
5. **머지는 사용자 승인 후에만**: 리뷰 결과와 PR 링크를 사용자에게 보여주고 승인을 기다린다.
   - 승인 전에는 `gh pr merge`를 실행하지 않는다. 승인은 해당 PR에만 유효하고 다른 PR로 이어지지 않는다.
   - 승인하면 머지하고, `main`을 최신으로 맞춘 뒤 머지된 로컬 브랜치를 정리한다.

## 하지 않는 것
- `main` 직접 커밋·푸시, force push, 사용자 승인 없는 머지
- 점검 실패 상태의 PR, 다른 기능이 섞인 PR
- 커밋 메시지·PR 본문에 비밀 값 포함

## PR 본문
`pr-checklist` §4 형식(무엇을 / 왜 / 어떻게 확인하는지)을 따른다.
